# Architecture

Mosaic is a SwiftUI app with AppKit where SwiftUI gets in the way of precise input, scrolling or window behavior. `Sources/Mosaic` holds the UI, workspace state, Contacts integration, media views and the AppleScript sender; `Sources/MosaicCore` holds the models, link detection and the read-only database reader (tested separately through SwiftPM); `Sources/CSQLite` exposes the system SQLite library. The Xcode target compiles the same sources.

## Zoom and motion

One persisted zoom (⌘+ / ⌘− / ⌘0, 80–160% in 10% steps) scales conversation content only: message and label fonts, bubble padding and corners, media and link-card dimensions, and the composer's font, insets and height bounds — the composer's `NSTextView` is updated in place, keeping text, selection, undo and marked text. Tile frames, the sidebar and the window chrome never scale. The `KeyboardRouter` consumes the zoom keys in the workspace window (so a press never fires both the monitor and the menu equivalent); the Workspace menu carries the same single action path.

There is no blanket animation suppression: every store mutation runs in a transaction without animation (`instantly`), which keeps tiles, layouts and dividers on-the-next-frame — one action's changes in one transaction (a nested `instantly` joins the outer one), since SwiftUI applies what is waiting at once, mid-change, when the next change comes in another — and the one declared motion is `NewMessageEffect` — a row appended at the thread's tail settles in once (classified by presentation identity, never by `onAppear`, so initial loads, older pages, reconnects and confirmations stay still). The offset is visual, not layout, so scroll pinning is untouched; Reduce Motion drops the movement and keeps a short fade; a Settings toggle turns it off.

## Menus

The menu bar (`WorkspaceCommands`) never reads the store's state. SwiftUI keeps an app's menus up to date at once, inside a change to what they read and before the new value is stored, and brings the window up to date in the same pass; when the Workspace menu read the open tiles (to enable Move Tile, Reopen Closed Tile), closing a tile updated the window while the tile was still open and the window then missed the change, so the tiles left stayed where they were. The menus read `store.menu` (`MenuState`) instead: values the store copies there on the next turn of the main queue after anything they come from changes. `scripts/app-check.sh` runs Mosaic as an app with its menus and the demo workspace, closes and opens tiles by the header's button, the menu and the sidebar, and checks the tiles drawn are the tiles open, where the layout puts them; CI runs it on every push, and again with a menu that reads the store, which it expects to fail.

## State

`WorkspaceStore` is `@Observable`, with the workspace split into separate fields so a view re-renders only when something it read changes — typing a draft re-renders one composer, not every row and tile. Each tile's last use (opened, focused, typed in, sent from) is counted, and a fifth conversation replaces the tile used longest ago in that tile's place, so the layout keeps its shape; an unsent New Message is never the one replaced while a conversation can be, and a protected tile (`Workspace.protectedIDs`, which ends when the tile closes) never is: when every tile is protected, `replacementChoice` asks the reader which one closes, or none. Sidebar pins (`Workspace.pinnedIDs`) only order the list — pinned rows first, in pin order — and are passed to the reader as `LoadRequest.keptIDs`, so a pinned conversation older than the 500 most recent is still listed. Closed and replaced tiles are remembered (the last twenty) for Reopen Closed Tile; a tile replaced to make room for a reopened one goes to the bottom of that list. Hiding (`hidden`) takes a conversation out of the sidebar only; Undo, Hidden Conversations and its next message bring it back. Open tiles, layout and drafts persist in UserDefaults; unsent composer work beside them (`SavedDrafts`, versioned: the paths of files waiting in each composer and each unsent New Message's recipients and creation date — never send outcomes, history or previews). Closing or replacing a tile never throws work away: a conversation keeps its text and waiting files, and a New Message with recipients, text or files stays in `composeDrafts` as a closed draft (an untouched one goes at once); every saved New Message comes back on relaunch, open or closed. Files still arriving when a tile closes are let go (their place is gone, so a late file is removed rather than landing in another draft). The sidebar's `draftSummaries` (presence and one line per draft) are rebuilt a moment after typing stops, so a keystroke never re-renders the list; the Drafts filter lists New Message drafts, then conversations with drafts. **Discard Draft** removes one draft and offers Undo for eight seconds (`offerUndo`), removing Mosaic's own copies of its pictures only once that has passed; a chosen file is never removed. a restored file that is gone shows as missing and blocks its send until removed; nothing is sent at launch. Message history, thumbnails, previews and contact names stay in memory. Sends are held as pending bubbles until the database reports them, then reconciled by text and time so a bubble keeps its identity. Nothing is retried automatically.

## Window chrome

The tall title bar is an empty AppKit toolbar (`WindowChrome`), not a SwiftUI toolbar item: the SwiftUI item put a nested hosting view in the title bar whose constraint updates could loop until AppKit raised an exception, which ended the app while histories loaded or tiles churned. AppKit's automatic title-bar dragging is off (`isMovable = false`), because in that region macOS moves the window on any press regardless of the view under the pointer; `WindowDragRegion` moves the window from the empty parts of the strip instead (`performDrag`, falling back to moving the frame), and a double-click there follows the System Settings title-bar action. As a safety net, `NSApplicationCrashOnExceptions` is off: an AppKit exception in a display cycle is logged, not fatal.

## Tiles

`TileLayout` plans every frame; `TileCanvas` places tiles through layout rather than offsets, so hit testing, carets and cursors line up with what is drawn. The canvas has the same view structure in every layout, so switching layouts resizes tiles instead of rebuilding them. Tile headers handle their own mouse events in AppKit (`TileHeaderHandle`): the × glyph is drawn by SwiftUI, its clicks are detected by the handle, and a header drag is followed with a local event monitor so it continues when SwiftUI re-inserts the raised tile's views. The Focus-layout chips are one AppKit view (`FocusChipBar`); when they do not fit the row, long names are cut to one shared width (short names stay whole) and below a minimum the chips show pictures only, with the full name as tooltip and accessibility label. The Workspace menu moves the focused tile (`Workspace.move`, sprung like a drag) and steps its size (`TileLayout.resized`, which changes the same proportions a divider drag does, taking the room from the neighbouring tile, row or column); the proportions stay in the view for the session. Every `NSViewRepresentable` reports its size from the layout proposal, never through Auto Layout, and no state changes during a SwiftUI update.

## Scrolling

`ScrollPinner` keeps each conversation's scroll position in AppKit, synchronously with size changes, in two modes. Near the bottom it follows the newest message through everything. Scrolled up, the reader is reading: SwiftUI hands the pinner a descriptor of the coming content (first/last row identity) before AppKit lays it out, so an append below moves nothing, a prepend above keeps the same rows, and a viewport resize keeps the row at the top of the view. For reflows (width or zoom changes) each row reports its frame in the thread's own scroll-invariant coordinate space into a `ThreadRowRegistry` (a plain class — no view invalidation), and the pinner puts the remembered message back at its remembered offset one turn later, once layout has reported the new frames. `ThinScroller` draws the same slim knob whether idle, hovered or dragged, redraws when its clip view moves, and — in the sidebar — classifies each trackpad gesture once (sideways swipe or scroll) so the knob never flashes for a swipe and the swiped row knows to drop its highlight. Bubbles are drawn text rather than selectable text views; each selectable `Text` on macOS is a full text view, and hundreds of them made opening and resizing slow.

A thread lays out only some of its loaded rows (`ThreadPresentation`), and about as many however far back the reader is: every scroll step costs SwiftUI work for each view laid out in the scroll view (its geometry is marked changed, and the thread's size is asked again), so a window that kept every row from where the reader turned back made each step dearer the further back they went. It starts with the newest 80 rows and grows upward a few rows at a time as the reader nears its top (well ahead: three views, at least 2,400 points); the next page of history (100 messages) is asked for when fewer than 150 loaded rows are left above, and a page read while a thread scrolls joins it once the threads are still (within 0.6 s). Rows wholly more than 3,200 points below the view are left out, a space as tall as they were standing in for them (`ThreadRowRegistry.heights`, from their last layout), so nothing in view moves — all but the newest (24, or as many as cover the view twice over), which stay laid out below the space; while the reader scrolls this waits until 160 rows are laid out (those among them), since taking rows away costs a frame too, and happens when they stop. Going back down lays them out again, a step at a time, and leaves rows far above out instead. Latest goes to those newest rows, laid out all along with their pictures, so going back from however far lays nothing out (laying out every row in between at once took seconds). Back at the newest message — Latest, or scrolled or dragged there — the rows above them go 24 at a time, 50 ms apart, then the rest (`ThreadPresentation.shed`, `release`): taking a long way's rows away at once held up the frame the reader arrived on. A match among the rows left out moves the window to it, the rows below it still left out. After a change of width or zoom the space is as tall as the rows were (scaled by the zoom): not exact, which moves nothing in view, since it is below the view; the rows are measured again as the reader gets to them. A bubble laid out again shows a picture already decoded from its first frame (`ThumbnailCache.decoded`), not a spinner. When the reader stops scrolling a long way back, 32 older rows are laid out ahead of them while nothing moves. While reading back, `ThreadStack` keeps room (12,000 points) above the rows and keeps the topmost row laid out in the last pass where it was: older rows come into the room, rows left out above leave room behind, and new rows make the thread taller at its end, so the scroll view needs no putting back in place for them (each time it did, the whole window was laid out twice more) and the scroller does not jump; the room is made again when it runs out, and goes at the newest message, at the start of the conversation, at the most a tile shows, and when the reader jumps into it with the scroller. `ThreadStack` keeps its rows' sizes between layout passes until SwiftUI reports the rows changed, so the size query each scroll step makes measures nothing.

## Sidebar

The list is a SwiftUI `List` for its swipe actions; the full list (`ConversationList` for All) stays alive, transparent and untouchable, under the Unread or Drafts list, so going back to All shows it as it was instead of inserting hundreds of rows. Rows are highlighted only by the keyboard; the pointer highlights nothing, so a swipe never sits against a hover highlight, and the keyboard's highlight is hidden while a swipe is under way. `SidebarKeyboard` gives the list the keyboard (⌘L): an invisible AppKit view becomes first responder, so the highlight follows real keyboard focus and clears when anything else is clicked. `KeyboardRouter` takes ⌘F, ⌘L, Tab and the search field's arrow keys in a local event monitor, ahead of the menu bar — except while the window's text field has marked text (an input method composing), when every key goes to the composition.

Opening a conversation — a click on its row, Return in the list or the search field, the menu, a drop — and Tab, a Focus chip, a click in a thread or on a header all go through `WorkspaceStore.requestComposerFocus`, which records a request (conversation and an increasing token) with `ComposerFocus`. The request is not proof of anything: `ComposerFocus` hands the keyboard over at a moment of rest (a run-loop observer just before the loop waits, after the event and the view updates it caused), only to the message field that is live in the workspace window at that moment, and completes the request only when that field is the window's first responder at a moment of rest. A failed or displaced hand-over is tried again a few times, then again when the field joins the window or the window becomes key; only the newest request counts, and any mouse press, ⌘F/⌘L, or closing or replacing the tile cancels it, so a request never takes the keyboard from something chosen after it. A field that already has the keyboard keeps its selection. The `ComposerFocus` category in the unified log (debug level) traces each request: the token, waits for the field, each hand-over's result and the first responder after it.

## Opening tiles

At launch (and on switching to Messages) the window says it is loading — outlined rows in the sidebar, a spinner in an empty workspace — instead of asking to connect, until the first read succeeds or fails. That first read is the list on its own (`LoadRequest.listOnly`: names, members, previews, unread counts, open conversations outside the list; no histories, no group-photo lookups), so the sidebar and the restored tiles appear in a fraction of a full load; the full load follows at once and fills the tiles' histories. Nothing is cached on disk for this.

A tile opens on its messages without waiting for a full load. The store keeps the histories it recently showed or fetched in memory (`historyCache`, sixteen conversations, least recently used dropped first; never written to disk), fetches the eight most recent conversations after the first load and any conversation whose row the pointer rests on for 150 ms (a sweep down the list fetches nothing; leaving the row drops a read not yet started), and fetches a single conversation's page (`MessagesReader.page(forChat:)`) when a tile opens on one it does not have. Reads ahead go one at a time, the most recently wanted first, at most eight waiting: the reader has one serial queue, so a pile of them would sit in front of the conversation you click. A tile opening on a fresh read takes a waiting read ahead's place and the rest wait until it has its messages; a conversation already being read ahead is shown from that read. The full load that follows brings the history up to date.

## Messages database

`MessagesDatabase` opens `chat.db` read-only with the WAL visible. A poll loads only when the database's `data_version` changed, and `FileChangeWatcher` on `chat.db` and its write-ahead log refreshes within a moment of Messages writing: 120 ms after a burst settles, and never more than 500 ms after it began, so a writer that never pauses still shows. The fallback poll (`RefreshPolicy`) runs every 3 s while Mosaic is in front, every second while a send awaits its row, and every 15 s in the background at utility priority; activation and wake check at once. The fixed statements (change probe, conversation list, histories, reactions, unread counts) are compiled once per connection and reset after each use; members are read only for the listed and open chats and attachments only for the page's own message IDs. Participants, attachments and typedstream bodies are decoded in `MosaicCore`. A load reads each open tile's newest 100 messages. Scrolling back reads only the 100 before the oldest one shown (`MessagesReader.earlierPage`), by a `(date, ROWID)` cursor — row values, so equal times neither repeat nor skip a message — and the store puts them above the others by message ID, up to 1,000. Later loads keep those earlier messages above the newest page and look up the reactions on them too (`LoadRequest.earlierRows`); their own rows are not read again, so an edit or unsend far up a long thread shows once the tile is reopened. When more than a page arrives at once, so the newest page no longer meets what was shown, the tile starts over from the newest page rather than show a gap.

A held tile is drawn where the pointer has it by a visual effect (`TileMotion`), which moves the finished tile without laying anything inside it out again; only that small view reads the pointer's position (`TileDragMotion`), so the workspace re-renders when the order changes, not on every move. Picking a tile up lifts it (1.5% larger, a deeper shadow, above the others); tiles it passes spring from their old places (`tileSprings`, offsets animated to zero), and on release it springs into its slot and comes back down. Shadows are drawn from the tile's rounded shape rather than from its contents. With Reduce Motion, tiles move in one step. A benchmark of a held tile moving over four 120-message tiles measured about 22 ms of main-thread work per frame before this change and about 12 ms after, on a CI virtual machine.

Recurring media work is bounded. Thumbnails decode three at a time, newest request first (the rows on screen are usually the latest), at one of three pixel sizes chosen from the bubble's size, the shared zoom and the screen's scale; they are keyed by file version (read off the main thread for every request, cache hits included, since a stat can stall on a file still arriving from iCloud), so a picture that finishes downloading decodes again, and a failure is retried after half a minute. Link previews fetch four at a time through `AsyncLimiter`, which hands a finishing slot straight to the next waiter; the most recent 200 are kept, with images downsampled to the card, and a failed fetch is retried after five minutes. Requests are shared per key (`SharedRequests`): a view that goes away leaves, and when the last one leaves the work is cancelled. Contacts are read for names and addresses only, with a note of which contacts have a photo; an avatar reads its contact's thumbnail when it is shown (`ContactPhotos`: three at a time, decoded to 120 pixels, the most recent 200 kept in memory), so a large address book's pictures are never all loaded or decoded on the main thread. A thread's rows, reactions and lookups are prepared once per change of its messages or reactions (`ThreadPresentation`), not on every render; a change of time zone or locale refreshes formatted dates. The Messages script is compiled once per launch, into a file that a helper process (`osascript`) runs for each send: NSAppleScript is main-thread only, so a send run inside Mosaic held the window until Messages answered, while the helper waits on its own main thread and Mosaic's stays free. Sends still go one at a time in the order Return accepted them; a refusal comes back with Messages' error (the Automation permission is named when that is what is missing), and a helper that ends without an answer is reported as uncertain, never resent. The helper is Mosaic's child process, so Automation permission stays Mosaic's. Because the window stays live, a message's row can arrive before its hand-off returns; a late error then leaves the row alone (it is the message, and is never offered for resending). Quitting while messages wait their turn asks first, and can wait for them (`SendActivity`). A text a process's arguments cannot carry (a NUL, or one near the size limit) is sent in process. Only when the helper cannot be started at all (nothing was sent) does Mosaic fall back to running the script itself. Compile and send durations are logged under the `bridge` category.

## Reactions, replies, edits, unread

The reader keeps reaction rows (`associated_message_type` 2000–3999) out of the history page and loads those pointing at the page's GUIDs separately; `Reactions.reduce` rebuilds the current state from whatever rows exist — per actor and part the latest row decides, a removal clears only the same actor's matching kind — so a deleted row simply disappears. Replies carry `thread_originator_guid`/part; originals above the page are fetched by GUID within the same chat (at most fifty), so a quote never needs the history above it and never shows another chat's message. Unsent rows keep their place with all content dropped at read time (so nothing stale can be copied, quoted or previewed). Unread counts are counted by the reader from a per-conversation seen boundary (a row id), incoming ordinary messages only; the boundary moves when the reader opens a conversation (from the list, the menu, a notification), when the tile they are in shows its newest message, or when they send. Being in a tile means its message field has the keyboard: the field reports taking and losing it (`composerTookKeyboard`/`composerLostKeyboard`), so a click or Tab into the tile reads it, and a tile that is merely open — however visible — counts what arrives in it as unread until then. Closing a tile reads nothing (a double click on its row, whose first click read it, puts that back). The thread reports when its tail is shown (`tailSeen`/`tailLeft`), and the tile the reader is in is read only while Mosaic is active, the window is key and neither minimized nor covered (its occlusion state), and the tile is in view — a Columns tile must be at least 80% inside the workspace's visible width (each tile reports this from its geometry), and in Focus only the focused tile counts; a tail shown while any of that is false waits and is read once it becomes true, unless the reader scrolled away or left the tile first. Opening reads at once rather than when the keyboard arrives, because in a quick run of openings each takes the keyboard from the one before, perhaps before it got there. A load counts unread messages from the boundaries as they were when it began; a conversation read while it was under way is counted again from its new boundary when the load is shown (from the open tile's newest messages, else by another load), so a reading is never undone by a load that started before it. Whether a conversation notifies depends only on whether the reader can see its tile, not on whether they are in it.

Find in Conversation keeps what is typed in the find bar's own state, so a keystroke redraws the bar alone; the words reach the tile 150 ms after typing stops. `FindIndex` works out the loaded matches once per query and history, `ThreadPresentation.findMatches` gives only the matching bubbles the words, and `MessageBubble` is `Equatable` (its closures left out; `nameContext` stands for what they read), so a new query redraws the matching bubbles, never the whole thread. 250 ms later the older history is searched by itself (`searchOlderHistory`, two characters or more): part after part of 2,000 rows by `MessagesReader.searchHistory` on a second, utility-priority connection (`historyReader`), so loading is never held up — from the oldest message the tile shows, by a (date, row) cursor, each row's body decoded (plain or rich text) and matched in Swift (so `%` and `_` are literal and rich bodies are covered), skipping reactions, activity and unsent rows. Where `chat_message_join` keeps `message_date`, a part reads in that column's order, which Messages' chat-and-date index serves without sorting the history. The search pauses at 500 matches or 250,000 rows (Search Further goes on); a search that a newer one or a cancel superseded publishes nothing. Stepping runs through the loaded matches and on into the older ones; an older one is shown through `MessagesReader.context` — 30 messages either side, read apart from the tile's newest page (so the 1,000-row ceiling and the page itself are untouched) — in a separate thread view whose tail never counts as read; Back to Latest drops it.

Notifications are opt-in (`notificationsEnabled`, Settings › Notifications, where the only permission prompt is). After each load, `noteNewMessages` compares the conversations' newest rows with the previous load's highest row (`notificationMark`, unset until a connection's first load, so launches and reconnects notify nothing); for the conversations with newer rows it asks the background connection (`MessagesReader.newestIncoming`, one indexed lookup each) for the newest ordinary incoming message — not a reaction, activity line, unsent message or your own — and posts one notification per message identity (`conversation#row`), skipping muted conversations (`mutedUntil`, Mosaic's own) and any the reader can see (`canSee`). Reading a conversation withdraws its notifications; clicking one runs `openFromNotification`, the usual opening path. The notifier is a service (`MessageNotifier`): the system notification center in the installed app, a recording in fixture runs, which never asks for permission or shows anything.

The details panel (`ConversationDetailsPanel`) merges `SharedContent` from the loaded messages with `SharedHistory` from the whole conversation (`MessagesReader.sharedHistory`, on the background connection when the panel opens, kept for a few conversations per session): attachment records through the chat join (not stickers, hidden files, link-preview payloads or unsent messages' files), and links from the messages whose text or rich body contains "http" or "www." (SQLite's `instr` finds them without decoding every message), the newest 1,000 of each, each item once. `SharedContentCache` works the content out again only when the messages or the history change, and the photo grid and the file and link lists (lazy, and `Equatable` on the cache's version) are drawn again only then: when the panel worked it all out on each redraw of its tile, a conversation that shared hundreds of photos and links slowed every change in the workspace. A picture's menu reads the local files worked out once, and the app a file opens in is asked of Launch Services once per kind of file (`AttachmentActions.defaultAppName`). A picture scrolled out of view leaves its decoded thumbnail to the cache.

Mosaic shows reactions and replies but does not send them: Messages' scripting dictionary sends only text and files (`TransportCapabilities.nativeReply` and `.nativeReaction` are false), and Mosaic does not imitate either with ordinary text.

## Composing

`ComposeDraft` and `Recipient` address a new message. `HandleForm` is the one reading of a handle for both comparing (`Recipient.key`, `ContactNames`) and routing (`Recipient.handle`): emails lowercased; a phone number in international form only when that is certain — written with "+" or an international prefix, or in the Mac's region's national form (a trunk 0, a North American ten-digit number, a fixed national length, the region's own calling code without "+") — and otherwise its digits as written, compared only with themselves and handed to Messages as typed. Nothing is matched by trailing digits, and no number is moved into another country. `WorkspaceStore.composeRoute` says where a New Message goes, and the To field shows it before anything is sent: the chosen conversation (`boundConversationID`, exactly that chat, or nowhere if it has gone), the only conversation with exactly these people, a choice when there are several (`conversations(with:)`, most recent first — Messages keeps one chat per service or address), a new iMessage conversation for one new person, or why it can't go (a new group: Messages offers no automation for creating one, and nothing is opened instead). `sendCompose` settles the target before waiting for imports, so recipient edits during that wait don't change it; after a send to a new person the tile records them (`routedTo`) — its To field is fixed, later sends and Try Again go to them, and adoption looks for their conversation. Sending to an existing conversation uses the chat's identifier in AppleScript; a new person goes through the iMessage account's participant. SMS or RCS for a new person isn't offered: a chat's service says what it was received over, not what a new one could be started with.

Pictures and files (`OutgoingAttachment`) wait in the composer and go out before the text, each as its own message. Pasted pictures are written to Mosaic's folder in Application Support; at send time every file is copied into `~/Library/Messages/.mosaic-outgoing/<id>/`, because Messages' sandbox reads attachments only from its own folders — a file handed over from anywhere else is accepted by AppleScript and then fails to send. The staged copy is made off the main thread and removed a few minutes later, once Messages has copied it into its Attachments folder — or at once when Messages refuses the send. Saves and copies of received files, and the launch cleanup of earlier leftovers (which skips every file a saved draft points at), also run off the main thread. A pending bubble with an empty text and the file as its attachment stands in until the database reports the sent message, which is how Messages records a picture. The + button is an AppKit view so the Photos grid can open in a popover card from it. The grid is Mosaic's own (`PhotoLibraryPicker`, on PhotoKit, with Photos access asked once): the system picker's card carries a selection label, a location notice and option buttons that cannot be removed, and its scroll bar grows under the pointer. Thumbnails come from `PHCachingImageManager`, which preheats a bounded window around the visible cells with the cells' own request; the selection is kept by identity (so a library change while the picker is open keeps it, and adding three photos never walks the library), and a change observer updates the grid. Chosen items are written out by `PHAssetResourceManager` (the edited rendition when there is one) into Mosaic's folder, three at a time in the order chosen (Photos may download each from iCloud and writes it progressively, so a large selection all at once would contend for disk and network), each appearing behind a placeholder as it lands; a write that fails removes its partial file; a Return pressed meanwhile waits for them. The strip's thumbnails come from a camera file's embedded preview when it has one.
