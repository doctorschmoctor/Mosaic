# Mosaic: research and implementation handoff for Claude

Prepared October 4, 2026. Repository baseline: `1367c41b18c923e9f84b11d1065f91ec423e7939`.

The objective is to make Mosaic faster and more capable while preserving its native macOS workspace, independent composers, reliable recipient routing, and read-only access to Messages' database. The explicitly requested features are animated sending/receiving, replies, reactions, and Command +/− zoom shared equally by every tile. This document proposes work; it does not implement app behavior.

## Recommended scope and sequence

Start with the correctness foundations, shared zoom, and message animations. Add received replies and reactions next. Native outbound replies and Tapbacks require a separate feasibility decision because the current Messages automation interface cannot express them.

| Delivery batch | Tasks | Result |
|---|---|---|
| 1. Establish evidence and fix correctness | F01–F03, P01, M01–M03, A03, Q01 | Reliable refresh detection, send/import state, attachment identity, and scrolling |
| 2. Deliver the requested interaction polish | Z01–Z03, A01–A02 | All tiles zoom together; new messages animate once without shifting history |
| 3. Make message history more complete | P02–P04, M04–M07, M09, X01 | Independent history loading, received reactions, reply relationships, honest quoted replies, edits/unsends, local unread counts |
| 4. Reduce recurring work | P05–P14, X04 | Scoped updates, bounded media work, more responsive sends, recoverable drafts |
| 5. Expand navigation and workspace tools | M10, X02–X03, X05–X09, Q02–Q03 | Search, saved workspaces, media tools, keyboard actions, privacy controls, release checks |
| 6. Evaluate larger architecture changes | P15, M08 | Virtualized history or alternative native-send integration only if evidence warrants it |

This is a backlog, not an instruction to ship every optional feature in one change. Each completed task should be a reviewable change with its acceptance criteria demonstrated. Apply Q01–Q03 as relevant in every batch; their placement in the table does not defer tests, documentation or build checks.

Priorities: **P0** = correctness/foundation; **P1** = requested feature or strong near-term value; **P2** = optional expansion or profiling-dependent optimization. Size: **S** = contained change; **M** = multiple components; **L** = substantial integration; **XL/spike** = feasibility unknown. Sizes are relative engineering estimates, not delivery promises.

## What the repository already does well

- `@Observable` state, ignored bookkeeping, unchanged-snapshot suppression, an equatable message list, and debounced draft persistence already reduce unnecessary work.
- Histories load only for open conversations; closed sidebar conversations carry summaries. There is already a database/WAL watcher, a 120 ms debounce, and a three-second fallback poll.
- Thumbnail decoding runs away from the main thread, deduplicates requests, and uses a cost-limited cache. Link previews already deduplicate requests and attempt to limit concurrency to four.
- Message `presentationID` survives database confirmation. AppKit controls handle precise focus, headers, composers, and scrolling.
- Attachment and link frames reserve space before media loads. Bubble text avoids hundreds of expensive selectable text views.

Preserve these benefits. Do not propose adding features that already exist: paste/drop attachments, the Photos picker, contact names, three tile layouts, independent drafts, keyboard traversal, incoming attachment saving, and a Latest button are present.

### Synthetic database experiment

An isolated SQLite WAL fixture contained 250,000 messages and 50,000 attachments, with only implicit ROWID indexes. The equivalent aggregate fingerprint was unchanged after updating an older message's text, `is_read`, and `error`, and renaming its chat. A retained read-only connection's `PRAGMA data_version` changed.

Across 20 warm queries, aggregate fingerprint median: **66.235 ms**; `data_version` median: **0.002 ms**. The saved probe was rerun successfully with medians **66.288 ms** and **0.002 ms**, confirming the missed-change result. The probe used Python 3.14.5 and SQLite 3.53.1; Mosaic links the macOS system SQLite library. This compares query primitives on an unindexed synthetic fixture, not end-to-end app performance or Apple's real indexes/library version. Do not present the ratio as an expected Mosaic speedup. See the companion [probe](/Users/deenradoncic/Desktop/code/Mosaic/docs/research/sqlite_probe.py) for reproduction.

SQLite explicitly requires comparing `data_version` on the **same connection**. Replacing the query without changing connection lifetime would be incorrect. A database-version change also does not identify which conversation changed. [SQLite data_version documentation](https://sqlite.org/pragma.html#pragma_data_version)

## Performance tasks

- [x] **P01 — Replace lossy aggregate change detection with a retained read-only reader (P0, L; depends F01).** Files: DB, Store, FileChangeWatcher. Own one SQLite read-only connection on a serial executor/actor or dedicated queue. Compare `PRAGMA data_version` between short, completed reads on that same connection, cache schema knowledge, and keep WAL visibility. Capture version/load bookkeeping so a commit racing a load is not marked as consumed. Reopen on database replacement/revocation, reset tokens on reopen, and force requested-history loads even when the database itself is unchanged. Do not hold an idle read transaction. **Accept:** unchanged polls avoid table aggregates; old-row edits, flags, renamed chats, membership changes, attachment updates and deletes refresh; WAL checkpoint/replacement and permissions failures recover. `data_version` is an invalidation token, not a per-chat delta feed. [SQLite documentation](https://sqlite.org/pragma.html#pragma_data_version)

- [x] **P02 — Separate sidebar summaries from individual tile histories (P1, L; depends P01, F03).** Files: DB, Store, Models. Replace the shared maximum history limit with a per-conversation request. Opening or extending one tile loads only that history, retaining the other histories and their pending messages. Start initial database and authorized Contacts loading independently, applying names as they arrive; the current startup waits for Contacts before refreshing Messages. Closed tiles should release history under a bounded policy. Return immutable snapshots and apply only to the request/mode generation that is still relevant. Initially refreshing the 500 summaries plus bounded open histories on a version change is acceptable; optimize further only after measurement. **Accept:** extending tile A to 500 messages leaves B–D at 100; slow Contacts does not delay initial histories; close/open during refresh produces no empty-history flash or stale publication; sidebar summary changes cannot erase pending sends.

- [ ] **P03 — Use cursor-based history pagination (P1, M; depends P02).** Files: DB, Store, ThreadUI. Fetch earlier pages using a stable `(date, ROWID)` cursor, a bounded limit, and `hasMore`, rather than re-reading a growing recent suffix. Merge pages by ID, separately load associated events, and support targeted context retrieval for search/reply navigation. Keep the 1,000-message ceiling until rendering is measured; a larger ceiling can be a later product choice. **Accept:** equal dates and inserts/deletes between pages yield no duplicates or skipped known rows; prepend preserves the reader's anchor; loading one page does not decode previous pages again. SQLite's row-value documentation explains comparison-based scrolling queries. [Row values and scrolling windows](https://sqlite.org/rowvalue.html#scrolling_window_queries)

- [ ] **P04 — Publish changed records and reconcile conservatively (P1, M; depends P02).** Files: Store, Reconciler. Maintain conversation lookup/order separately from history revisions and apply a transaction with a change set: inserted, updated, removed, and pending-confirmed messages. Do not rely solely on `MAX(ROWID)`; older rows, receipts, reactions and deletions must still be considered. A retained `data_version` cannot tell which rows changed, so bounded rereads/diffs are the safe first implementation. **Accept:** one chat's receipt update does not rebuild every other thread; snapshots that contain no visible changes publish nothing; a reconnect/forced refresh does not replay message-entry effects.

- [ ] **P05 — Narrow observation to each tile where profiling warrants it (P2, M; depends F01, P04).** Files: Store, ThreadUI, WorkspaceUI. If material, introduce stable per-tile observable state and separate sidebar summaries, without replacing a tile object during updates. **Accept:** typing/importing in A leaves B–D's histories and editor updates quiet in traces; focus, drafts and scroll state survive reorder/layout changes. ## Cross-feature acceptance matrix

| Scenario | Required result |
|---|---|
| Incoming message while at the bottom | Tail follows; only that new bubble animates |
| Incoming message while reading older history | Same visible message/offset; local unread increases; Latest shows count |
| Load earlier history | Anchor preserved; no old-row entry animation; other tiles retain their depth |
| Optimistic send becomes a database message | Same presentation ID, no duplicate bubble/effect, actual status replaces local submission state |
| Three selected photos finish in reverse order | Selected order is retained in draft and outgoing batch |
| iCloud export takes more than 15 seconds | Clear pending/progress state; no silent partial send |
| A tile closes/reopens or is replaced during import/send | Captured send recipient remains fixed; old import cannot attach to a new draft; draft ownership survives |
| Command +/−/0 from any tile | Every tile uses the same scale; correct menu/limits; editing focus and keyboard behavior remain valid |
| Zoom/resize/reaction badge/reply excerpt changes height | Tail or stable message anchor is preserved; geometry/hit targets/carets agree |
| Reduce Motion or animation preference off | No positional bubble motion; every action remains understandable and accessible |
| Reaction targets a message outside the loaded page | No stray ordinary reaction bubble; resolve association or show an explicit unavailable target |
| A reaction row is deleted | Badge disappears on next valid refresh without requiring new message maxima |
| Native reply/Tapback transport unavailable | Honest quoted-reply/Message-handoff options; no false transmission success |
| Earlier message is edited or unsent | Current projection/search/copy/quote content updates; no stale exposure through caches |
| Database/WAL recreated or app reactivated | Reader reconnects/checks promptly; last good content survives temporary errors |

## Performance goals to validate, not claim as measured

Use F01 to choose final budgets on named test hardware. Reasonable initial review targets are:

- No table-wide aggregate query on an unchanged idle poll.
- No history-depth increase in tiles that did not request another page.
- Pending-send visual feedback within roughly 100 ms after an accepted, ready send; import waits are shown immediately. A synchronously blocking bridge may require P13 before this is achievable under slow automation.
- Database-commit-to-visible-message p95 under roughly 500 ms while active, excluding OS/file-system delays; measure watcher debounce and the complete load/publish path.
- Main-thread app work comfortably under the refresh interval: 16.7 ms at 60 Hz and 8.3 ms at 120 Hz are frame budgets, not available CPU allowances for every component. Record hitches instead of merely reporting average FPS.
- Bounded decode/fetch queues and bounded caches; repeated open/scroll/close cycles should settle into a plateau after warm-up, without an ever-growing retention trend. Do not assert a fixed RSS cap based solely on NSCache settings.

Keep performance traces and the correctness tests together: a faster implementation that loses an attachment, jumps the reading anchor, or chooses the wrong recipient does not satisfy the task.
